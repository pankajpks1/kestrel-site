A feature flag is a named switch your app asks Kestrel about. For each person, Kestrel answers with one of the flag's variants — on or off, or a value such as a string or a JSON object — and your code acts on it. Who gets which variant is set in Kestrel, so you can roll a change out gradually, limit it to a cohort, or turn it off, all without a release.

Open Feature Flags in the sidebar to see your flags. Creating and changing flags needs the Analyst role or higher.

Flag types

Click New Feature Flag and choose a type:

TypeUse it toStarts with
Feature GateTurn a feature on or off.Two variants: On, valued true, and Off, valued false (the control).
Dynamic ConfigSend your app a setting or payload you can change at any time.One variant, Config Key, valued with the empty JSON object {}.
ExperimentSplit people between versions of a feature and measure the difference.Two variants, control and treatment, half each, valued "control" and "treatment".

For a Feature Gate or a Dynamic Config, give the flag a name and a key. The key is what your code asks for. Kestrel suggests one from the name — "Project Launch" becomes project_launch — and you can type your own. An Experiment flag is made for you when you create an experiment: choose New Experiment from the dialog.

A new flag is a Draft: it serves nothing until it has a rollout group and is enabled.

Variants and values

The Variants card on the flag's Overview lists what the flag can serve.

  • Feature Gate: On and Off are fixed. People in a rollout group get On; everyone else gets nothing from Kestrel, so your code's fallback applies.
  • Experiment: each variant has a name, a description and a value. Click + Add for another variant, up to 10. The control's name can't be changed, and the control can't be deleted.
  • Dynamic Config: each variant has a name and a value. Everyone in a rollout group gets the first variant. Any further variant is served only to the QA testers you assign it to.

Variant values on Experiment and Dynamic Config flags are either String or JSON, chosen from the menu on the Value column. All variants of a flag use the same type.

  • A JSON value must be an object, such as {"color": "blue", "limit": 20}. A field shows red until what you've typed is a valid object.
  • Each value can be up to 32 KB.
  • Switching to JSON sets every value to {}. Switching to String sets each value to its variant's name.

Deleting a variant gives its share of traffic to the first variant left, and removes it from any QA tester who had it.

Sticky variants

Tick Sticky on a variant to keep it with each person who is served it. Once someone has a sticky variant, they keep it even if you later change the percentages or splits, or they no longer fall in any rollout group. A control can't be sticky.

Sticky variants last until the flag is disabled. Disabling a flag forgets them, so when it is enabled again everyone is placed afresh.

QA testers

QA testers get a variant of your choosing, so you can check each one before real users see it. Under QA, click + Add Testers, search for a user by name or distinct ID, and pick them. A new tester gets the control; use the menu in the Variant column to change it. Hover over a row and click the bin to remove a tester.

  • A tester's variant comes before everything else: before a sticky variant and before the rollout groups. They don't need to be in any group.
  • Testers are matched on their distinct ID, and only while the flag is enabled.
  • The answer Kestrel sends for a tester is marked as a QA tester's, and the SDK records that on the exposure event as $is_qa_tester.

Rollout groups

Rollout groups decide who is served. Click + Add Rollout Group to add one; it starts with all users at 100%. Each group has:

  • Filter by User Cohort: All Users, or one of your saved cohorts. Click + Filter to pick a cohort, and the × on it to go back to All Users. The number of users in the cohort is shown alongside.
  • Percentage: the share of the group who are served, in whole percents.
  • On an Experiment flag, a split for each variant: how the people served are divided between the variants. A group's splits must add up to 100%.

Groups are checked from top to bottom. A person is served by the first group they fall into; groups below it are not checked. Someone who falls into no group is served nothing by this flag, and your code's fallback applies. A flag can have up to 50 groups. To remove one, open its menu and choose Delete.

How people are placed

Kestrel places people by hashing the flag's Assignment Key — the user's distinct ID, or for a flag set to use it, the device ID. Nothing random is stored, so the same person always gets the same answer while the flag stays the same.

  • Whether someone is inside a group's percentage and which variant they get are worked out separately. Raising a percentage only adds people, and everyone already served keeps their variant. Lowering it removes people.
  • Changing an Experiment flag's splits moves some people to another variant, unless their variant is sticky.
  • Cohort membership is checked for the person's distinct ID when your app asks for flags, and remembered for up to 5 minutes.

The Assignment Key is shown on the flag's Configuration tab. It can't be changed once the flag has been enabled.

Saving changes

Changes to variants, QA testers and rollout groups are a draft until you click Save at the top of the page; Cancel discards them. Once saved, new requests for flags get the change within about 10 seconds. A page or app that has already fetched its flags keeps what it has until it fetches again.

Enable, disable and archive

The Status card shows where the flag stands:

  • Draft — never enabled and no rollout group yet. Configure Flag adds a first rollout group.
  • Disabled — set up but not serving. Enable Flag starts serving. A flag needs at least one rollout group to be enabled.
  • Enabled — serving, with the date it was last enabled. Disable Flag stops it: every request then gets your code's fallback, and sticky variants are forgotten.

You can also switch a flag on or off from the Status column of the Feature Flags list. The list shows each flag's type, its Daily Usage over the last 30 days, when it was enabled, its tags, when it last changed and who created it.

The ⋯ menu on a flag's page has:

  • Rename.
  • Duplicate — a new, disabled flag named "Copy of …", with the same variants, rollout groups and QA testers.
  • Archive — takes the flag off the list. Archiving doesn't stop it serving: disable it first if it should stop.
  • Delete — only for a flag that isn't enabled. Disable it first.
  • History — who changed what, and when.
  • Pin for Project.

Exposures

When your code reads a flag, the SDK records an $experiment_started event with the flag's key as Experiment name and the variant served as Variant name. The Exposures card counts the people first exposed to each variant, per day, over the last 30 days, and the list's Daily Usage is built from the same events. If your app records exposures under a different event or property names, set them in your project's settings under Experimentation so Kestrel reads them.

Implementation

The Code Snippets button on a flag's Status card opens this section.

Web

Turn flags on when you start the Kestrel web SDK (@rivero/kestrel-browser). The SDK fetches the person's variants as soon as it starts, and again whenever identify changes who they are.

import kestrel from "@rivero/kestrel-browser";

kestrel.init("YOUR_PROJECT_TOKEN", {
  api_host: "YOUR_KESTREL_INGEST_URL",
  flags: true,
});

Then read a flag by its key. Every call takes a fallback, returned when the flag is disabled, the person isn't in any rollout group, the key doesn't exist or flags couldn't be fetched.

// A Feature Gate: true or false
if (await kestrel.flags.is_enabled("project_launch", false)) {
  showNewLauncher();
}

// An Experiment or Dynamic Config flag: the variant's value
const color = await kestrel.flags.get_variant_value("button_color", "blue");
const config = await kestrel.flags.get_variant_value("checkout_config", {});

// The whole variant: its key (the variant's name) and its value
const variant = await kestrel.flags.get_variant("button_color", { key: "control", value: "blue" });

These wait for the fetch to finish. Each has a _sync form — is_enabled_sync, get_variant_value_sync, get_variant_sync — that answers at once and returns the fallback if flags haven't arrived yet. await kestrel.flags.when_ready() waits until they have; kestrel.flags.load_flags() fetches them again.

The first time each flag is read after a fetch, the SDK records the exposure for you.

To keep variants between page loads, add persistence. Variants are kept in the browser for persistenceTtlMs (24 hours if you leave it out):

kestrel.init("YOUR_PROJECT_TOKEN", {
  api_host: "YOUR_KESTREL_INGEST_URL",
  flags: {
    persistence: {
      variantLookupPolicy: "persistenceUntilNetworkSuccess",
      persistenceTtlMs: 24 * 60 * 60 * 1000,
    },
  },
});

With persistenceUntilNetworkSuccess, a kept variant is used straight away until a fresh fetch succeeds. With networkFirst, the SDK waits for the fetch and falls back to the kept variants only if it fails.

Android, iOS and servers

The Kestrel Android and iOS SDKs don't fetch flags themselves. From a mobile app, or from your own server, ask Kestrel's flags endpoint on your ingest URL directly:

GET YOUR_KESTREL_INGEST_URL/flags?context={"distinct_id":"user-123","device_id":"device-456"}
Authorization: Basic base64("YOUR_PROJECT_TOKEN:")

The context is JSON, URL-encoded. distinct_id is required; include device_id for flags whose Assignment Key is the device ID. Instead of the header you can pass token=YOUR_PROJECT_TOKEN in the query string. The answer lists every enabled flag that serves this person a variant:

{
  "flags": {
    "project_launch": { "variant_key": "On", "variant_value": true },
    "button_color": {
      "variant_key": "treatment",
      "variant_value": "green",
      "experiment_id": "…",
      "is_experiment_active": true
    }
  }
}
  • A flag that serves this person nothing is left out: use your fallback for any key that's missing.
  • experiment_id and is_experiment_active appear when the flag belongs to an experiment, and is_qa_tester appears, set to true, for a QA tester.
  • When you use a variant, track the exposure yourself: an $experiment_started event for that person, with Experiment name set to the flag's key and Variant name to variant_key.
  • A missing or malformed context gets a 400 and an unknown token a 401. Requests are rate limited per client address and per project; past a limit the answer is a 429 with a Retry-After header. If flags are unavailable the answer is a 503 — use your fallbacks.
