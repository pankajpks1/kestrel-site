If your events already live in a data warehouse — BigQuery, Snowflake or Redshift — you can load them into Kestrel with its /import API. Kestrel does not read your warehouse on a schedule today; an import is a script you run, once for your history and then as often as you like for new rows.

1. Shape each row as an event

Write a query that returns one row per event, with these columns:

FieldWhat goes in it
eventThe event's name, such as Signed Up.
properties.timeWhen it happened, in Unix seconds or milliseconds (UTC).
properties.distinct_idThe person: their user id once known, otherwise a device id.
properties.$insert_idA unique id per event, such as your table's primary key. An event sent twice with the same id is counted once, so a failed import can simply be run again.
any other properties.*The event's properties, as you want them to appear in reports.

2. Send it in batches

Each request to /import carries up to 2,000 events and 10 MB, as a JSON array or one event per line (gzip welcome), with your project token as the username of a Basic Authorization header:

curl https://YOUR-KESTREL-ADDRESS/import \
  -u "YOUR_PROJECT_TOKEN:" \
  -H "Content-Type: application/x-ndjson" \
  --data-binary @events.ndjson

Run the query in your warehouse, write the result as newline-delimited JSON (BigQuery's EXPORT DATA, Snowflake's COPY INTO an external stage, Redshift's UNLOAD), split it into files of 2,000 events, and send each file. Events older than two years are refused, as Kestrel keeps two years of history.

3. Check it arrived

Each reply says how many events were accepted and lists any that were not, with the reason. Then open an Insights report on one of the imported events over the imported dates and compare its total with a COUNT(*) in your warehouse.
