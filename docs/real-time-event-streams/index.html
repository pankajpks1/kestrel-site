Real-time event streams

Send events to your own web service within seconds of arriving, filtered and shaped the way you want.

A real-time event stream delivers events to an HTTPS endpoint of yours as they are received, in batches, with a body you design. Streams are in beta. Setting one up needs the Project Admin role. Open Data › Destinations › Streams.

Set up a stream

  1. Add a destination: a name, an https:// URL and how to authenticate — an API key in a header you name, a bearer token, or none. Kestrel tests it when you save by posting an empty batch. A 401 or 403 marks the destination auth error.
  2. Create the stream on that destination and choose the event types to send. At least one is required; there is no "all events". A stream takes up to 500.
  3. Optionally add up to 20 property conditions. An event must meet all of them. The operators are equals, does not equal, contains, does not contain, is set, is not set, greater than and less than.
  4. Write the payload template. It is checked and previewed when you save.

The stream is enabled when saved. Filtering happens as events are received, so events that don't match cost nothing.

The payload template

The template is JSON with values filled in by {{ … }}. It is rendered once per event. These variables are available:

VariableValue
event_nameThe event's name.
event_timeWhen it happened, as an ISO 8601 timestamp.
distinct_idThe user's distinct ID.
insert_idThe event's unique ID. Use it to ignore duplicates.
project_idYour project's ID.
propertiesThe event's properties. Reach one with properties.plan or properties['plan']; use [0] to pick an item from a list.

Filters go after a pipe: default, upcase, downcase, capitalize, strip, append, prepend, replace, size and json, for example {{ properties.plan | default: "free" }}. {% comment %}…{% endcomment %} is also allowed. Anything else is rejected. Templates can be up to 20,000 characters, and nothing in them can run code.

Inside a JSON string a value is escaped for you, so "{{ properties.plan }}" is always valid. Outside a string it is written as a JSON value: numbers stay numbers and a missing value is null.

Delivery

  • Events go out as one POST with a JSON array of the rendered events (an array even for one event). A batch is sent at 500 events, or 5 seconds after its first event, whichever comes first.
  • Delivery is at least once: an event can arrive more than once, so deduplicate on insert_id.
  • A failed batch is tried up to 4 more times, waiting 0.2, 1, 5 and 30 seconds. On a 429, Kestrel waits for the Retry-After you send, up to 10 seconds. Other 4xx answers are retried too.
  • A 401 or 403 stops at once as an authentication error.
  • An event your template can't render is logged and skipped; the rest of the batch is sent.

When a stream stops

A stream whose destination fails authentication, or that runs out of retries, moves to the error state and pauses. A paused stream keeps no backlog: events that arrive while it is paused are not sent later. Enabling the stream again clears the error and resumes from then on.

Monitoring

  • Metrics show events delivered, events failed, batches and delivery time per minute.
  • The failed events log records, per minute, the status code, the kind of error (authentication, rate limited, server, client, network or template), how many events and the message.
  • The audit log lists changes to streams and destinations, with the time and who made them.
