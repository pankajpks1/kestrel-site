Cohort sync

Send a cohort's members to another tool, once or on a schedule, and keep that tool up to date as users enter and leave.

Cohort sync sends the members of a cohort to a connected destination — a messaging, advertising or other tool, or your own web service — so you can act on the group there. A sync can run once or keep running, sending only what changed.

Connect a destination

  1. Go to Data › Destinations and open the library.
  2. Choose a destination of type Cohorts and fill in its form: a name, the credentials the tool asks for, and the user ID property that identifies a user in that tool.
  3. Under Properties To Export, choose the profile properties to send along with each user.

Secrets such as passwords and API keys are stored sealed and are never shown again after you save them.

Start a sync

  1. Open the destination's connection and its Syncs tab, then choose to create a sync — or open a cohort's ⋯ menu in Lexicon › Cohorts and choose Export.
  2. Pick one or more cohorts.
  3. Choose One-time export (send the cohort's users now, once) or Recurring sync (keep the destination up to date).
  4. Choose Start Sync.

Group cohorts can't be exported.

What each run sends

The first run sends the whole cohort. Later runs send only the difference since the last successful run: users who entered the cohort are added and users who left are removed. If the last successful run is more than 3 days old, the next run sends the whole cohort again. A failed run keeps the earlier baseline, so the next one catches up.

A recurring sync runs every 15 or 30 minutes, or every 2 hours, depending on the destination. Syncs on one connection run one after another.

Each run's overview shows how many users were exported and removed, and you can download the run's users as a CSV with distinct_id, the destination's user ID and the operation (add, remove or no-op).

Custom Webhook

The Custom Webhook destination posts to a URL you provide, with optional username and password (HTTP Basic). Each request is a JSON object with an action of members (a whole-cohort run), add_members or remove_members, and a parameters object holding the project ID, the cohort's name, ID and description, a session ID shared by every call of the run, page_info (total_pages and page_count, counting from 1) and the members list. Each member carries email, first_name, last_name, phone_number, its distinct ID, the destination's user ID, and any properties you chose to export.

Each call holds at most 1,000 users, so a large cohort arrives as several pages. Reply with a 2xx status. You can also reply with a body such as {"status": "failure", "error": {"message": "…", "code": 400}} to report a problem.

Failures and pauses

  • A 429, a 5xx or no answer is retried up to 5 more times over about a minute. If it still fails, the run is marked failed and the next scheduled run tries again.
  • A 400, 401, 403 or 404 pauses the sync and its connection, and shows the reason. Fix the cause (for example, new credentials), then reconnect.

Limits

  • A project can have up to 60 recurring syncs, across all destinations.
  • A cohort can have up to 10 million users. A larger one isn't sent; narrow it or split it.
